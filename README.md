# AZS-project

Учебный проект оптимизации поставок топлива с нефтебаз в сеть АЗС.
Авторы: Тумасян Тигран, Москалев Павел.

Текущая версия проверяет ограничения, находит оптимальный план с помощью
SciPy/HiGHS и выводит стоимость, остатки и показатели расчёта.
Исходные данные загружаются из JSON, результат можно сохранить в JSON.
Доступны консольный режим, JSON API и веб-интерфейс: загрузка сценария,
редактирование JSON, проверка выполнимости, выбор метода и просмотр плана
таблицами. Сравнение режимов выполняется из консоли.

## Запуск

Проверено на Python 3.13.5. Из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
python -m pytest -q
```

Если окружение уже создано и зависимости установлены, достаточно активировать
его. В IDE выбрать интерпретатор `.venv/bin/python`.

Загрузка сценария и сохранение результата:

```bash
python main.py --input data/example.json
python main.py --input data/example.json --method highs-ds --output data/result.json
python -m json.tool data/result.json
```

Выбор режима и сравнение:

```bash
python main.py --method highs
python main.py --method highs-ds
python main.py --method highs-ipm
python main.py --compare
python main.py --input data/example.json --compare --runs 20
```

| Параметр | Назначение | По умолчанию |
|---|---|---|
| `--input` | JSON-файл с исходными данными | `data/example.json` рядом с `main.py` |
| `--output` | JSON-файл результата одиночного расчёта | Сохранение включается при указании пути |
| `--method` | `highs`, `highs-ds` или `highs-ipm` | `highs` |
| `--compare` | Сравнить все три режима на одном сценарии | Выключен |
| `--runs` | Число измеряемых запусков каждого режима, минимум 1 | 5 |

В режиме `--compare` сравниваются все три режима, независимо от `--method`.
Параметры `--compare` и `--output` несовместимы; входной и выходной файлы
должны быть разными. Каталог выходного файла должен существовать.
Относительные пути из аргументов отсчитываются от текущей рабочей папки;
входной файл по умолчанию находится относительно расположения `main.py`.

## Веб-интерфейс

В активированном окружении из корня проекта запустить сервер:

```bash
python api.py
```

Открыть [http://127.0.0.1:8000/](http://127.0.0.1:8000/).
Сервер должен оставаться работающим; остановка — `Ctrl + C`.
После изменения Python-кода сервер нужно перезапустить.

Порядок работы:

1. Выбрать файл `data/example.json` или вставить сценарий в текстовое поле.
2. При необходимости изменить JSON.
3. Нажать «Проверить данные»: для примера общий запас — 500 м³,
   необходимые поставки — 432 м³.
4. Выбрать режим решателя и нажать «Рассчитать план».
5. Изучить стоимость, метрики, таблицу поставок, отгрузки и остатки нефтебаз,
   поступления и остатки АЗС. Ожидаемая стоимость примера — 110310 руб.
6. Раскрыть «Полный ответ API в JSON» для просмотра исходных значений результата.

При изменении сценария или метода предыдущий результат очищается.
Во время загрузки файла и обработки запроса поля и кнопки временно отключаются.
Ошибки ввода, невыполнимость задачи и ошибки запросов отображаются на странице.
Числа в таблицах округляются максимум до трёх знаков после запятой;
полный ответ JSON выводится с отступами без предварительного округления.

Страница открывается через сервер Flask по указанному адресу. Ввод исходных
данных пока выполняется через JSON; отдельные редактируемые таблицы нефтебаз,
АЗС и тарифов — следующий этап. Расчёт в браузере не сохраняет файл на диске.

## API

API доступен после запуска `python api.py` на `127.0.0.1:8000`.

| Метод и адрес | Назначение |
|---|---|
| `GET /api/health` | Проверка работы сервера, ответ `{"status": "ok"}` |
| `POST /api/validate` | Проверка структуры и значений сценария, предварительная диагностика выполнимости |
| `POST /api/optimize?method=highs` | Поиск оптимального плана и выдача результата со сводкой и метриками |

Оба POST-запроса принимают сценарий с разделами `depots`, `stations`, `costs`
и заголовком `Content-Type: application/json`. Формат совпадает с
`data/example.json`. Для расчёта параметр `method` передаётся в адресе запроса:
`highs`, `highs-ds` или `highs-ipm`; по умолчанию — `highs`.

Ответ `/api/validate` содержит `status` (`feasible` или `infeasible`),
`feasible`, `station_ids`, `minimum_delivery`, `available_capacity`,
`total_stock`, `total_required` и список `violations`.
Проверка выполняется без вызова решателя. Формат ответа `/api/optimize`
описан в разделе «Данные и JSON».

Примеры запросов во втором терминале из корня проекта:

```bash
curl -sS http://127.0.0.1:8000/api/health

curl -sS -X POST http://127.0.0.1:8000/api/validate \
  -H "Content-Type: application/json" \
  --data-binary @data/example.json \
  | python -m json.tool

curl -sS -X POST \
  "http://127.0.0.1:8000/api/optimize?method=highs-ds" \
  -H "Content-Type: application/json" \
  --data-binary @data/example.json \
  --output data/result_api.json

python -m json.tool data/result_api.json
```

Параметр `--output` у `curl` сохраняет ответ в файл. Сам API файлы результатов
не создаёт. Ответ может быть записан в одну строку: это корректный JSON.
`python -m json.tool` показывает его с отступами, не изменяя исходный файл.

| HTTP-код | Значение |
|---|---|
| `200` | Запрос обработан; результат определяется полями `status` и `feasible` для проверки или `status` для расчёта |
| `400` | Некорректные данные, неизвестный режим решателя или ошибка синтаксиса JSON |
| `404` | Адрес не найден |
| `405` | Неподдерживаемый HTTP-метод |
| `415` | Не указан подходящий тип содержимого JSON |
| `500` | Ошибка расчёта или внутренняя ошибка сервера |

Невыполнимая задача возвращает HTTP `200` со статусом `infeasible`;
остановка по лимиту — HTTP `200` со статусом `limit`. Код `200` сам по себе
не подтверждает наличие оптимального плана. Ошибки данных имеют статус
`invalid_data`, ошибки HTTP-запросов — `invalid_request`, внутренние ошибки —
`error`. Ответы об ошибках передаются в JSON с полем `message`.

## Данные и JSON

Сценарий содержит три обязательных раздела: `depots`, `stations` и `costs`.
Минимальный пример формата для одной нефтебазы и одной АЗС:

```json
{
  "depots": [
    {"id": "B1", "stock": 120}
  ],
  "stations": [
    {"id": "S1", "remaining": 10, "demand": 30, "safety": 5, "capacity": 60}
  ],
  "costs": [[220]]
}
```

`stock` — запас нефтебазы; `remaining` — начальный остаток АЗС;
`demand` — потребление за период; `safety` — страховой запас;
`capacity` — вместимость. Объёмы задаются в м³, тарифы — в руб./м³.
Строки `costs` идут в порядке объектов `depots`, столбцы — `stations`.
Данные и тарифы демонстрационного сценария учебные.

`load_problem(path)` читает UTF-8 JSON и вызывает `problem_from_dict(data)`.
Проверяются обязательные и неизвестные поля, типы объектов и массивов,
идентификаторы, исходные объёмы и размеры матрицы тарифов. Числа должны быть
конечными и неотрицательными; `true`/`false` не принимаются как числовые
параметры. Значения `NaN` и `Infinity` отклоняются.
Некорректные данные вызывают `ValueError`, ошибки доступа к файлу — `OSError`;
`main.py` выводит сообщения об этих ошибках.

`result_to_dict(result, depots, stations)` подготавливает результат,
`save_result(path, result, depots, stations)` сохраняет его в UTF-8 JSON.
Ответ содержит `status`, `message`, `depot_ids`, `station_ids`, `deliveries`,
`total_cost`, `summary` и `metrics`. Идентификаторы задают порядок строк и
столбцов матриц результата. Массивы NumPy преобразуются в списки,
отсутствующие значения — в `null`. Вычисленные значения сохраняются без
предварительного округления. `metrics.solver_seconds` хранит время в секундах,
в терминале и браузере оно отображается в миллисекундах.

## Модель

Один вид топлива, один период, поставки до расходования. Все направления
доступны, объёмы непрерывные, единица измерения — м³.
Строки `x[i,j]` соответствуют нефтебазам, столбцы — АЗС.

Тариф `c[i,j]` задаёт стоимость доставки 1 м³ по направлению, руб./м³.
Минимизируется суммарная стоимость перевозок:

```text
Z = sum_i sum_j c[i,j] * x[i,j] -> min
```

Направления между нефтебазами и АЗС заданы заранее. Модель определяет объёмы
поставок; дороги, порядок посещения АЗС и назначение бензовозов в неё не входят.

Проверяются четыре ограничения:

```text
sum_j x[i,j] <= a[i]                   запас нефтебазы
r[j] + sum_i x[i,j] - d[j] >= s[j]     страховой запас после потребления
r[j] + sum_i x[i,j] <= V[j]            вместимость при поставке
x[i,j] >= 0                           неотрицательность
```

`check_plan(depots, stations, deliveries)` возвращает список нарушений;
пустой список означает допустимость заданного плана. Некорректные данные
вызывают `ValueError`.

`check_feasibility(depots, stations)` возвращает отчёт с минимальными поставками
`q = max(0, d+s-r)`, свободной вместимостью `u = V-r` и причинами невыполнимости.
Проверяются `q[j] <= u[j]` и `sum(q) <= sum(a)`. Эти условия достаточны для
базовой модели со всеми доступными направлениями. Сравнения учитывают
абсолютный и относительный допуски `1e-7`: `feasible=True` означает, что
диагностика пройдена с этой точностью, и само по себе не задаёт план поставок.

`build_constraints(depots, stations)` возвращает `A_ub`, `b_ub`, `bounds`,
порядок переменных `variable_ids` и подписи строк `row_labels`:

```text
A_ub @ x_vector <= b_ub
bounds = (0, None) для каждой переменной
x_vector = [x11, ..., x1n, x21, ..., xmn]
```

Порядок блоков строк: запасы нефтебаз → минимальные поступления на АЗС →
вместимость АЗС. Размер `A_ub` — `(m + 2*n, m*n)`.
Неотрицательность передаётся через `bounds`, поэтому дополнительных строк
для неё нет. Матрицы содержат исходные коэффициенты без округления и
формируются даже для корректно заданной невыполнимой задачи.

Матрица в выводе «План поставок, м³» — результат `deliveries`.
Её элемент показывает объём поставки по направлению; ноль означает,
что направление не используется в найденном плане.
`A_ub` содержит коэффициенты ограничений для решателя.

## Оптимизация

`validate_costs(costs, shape)` проверяет размеры матрицы тарифов,
неотрицательность и конечность чисел.

`optimize_plan(depots, stations, costs, method="highs")` проверяет данные,
формирует ограничения и вызывает `scipy.optimize.linprog`. Найденный план
независимо проверяется через `check_plan`, стоимость пересчитывается по тарифам.
Некорректные входные данные вызывают `ValueError`.

Результат `OptimizationResult` содержит статус, сообщение, матрицу поставок,
стоимость, сводку `PlanSummary` и метрики `SolverMetrics`.

| Статус | Значение |
|---|---|
| `optimal` | Оптимальный план найден и прошёл проверку |
| `infeasible` | При текущих требованиях допустимого плана нет |
| `limit` | Расчёт остановлен по лимиту, оптимум не подтверждён |
| `error` | Ошибка решателя, проверки результата или формирования сводки |

Для статусов без подтверждённого оптимума поставки, стоимость и сводка
равны `None`. Метрики доступны после вызова решателя; при отклонении задачи
предварительной проверкой они равны `None`.

Сводка включает отгрузки и оставшиеся запасы нефтебаз, поступления на АЗС,
запасы до и после потребления, стоимость поставок по каждому направлению.
Числа округляются только при выводе.

Текущий `data/example.json` содержит 5 нефтебаз и 15 АЗС. Матрицы тарифов и
поставок имеют размер `5 × 15`: 75 переменных. Матрица ограничений —
`35 × 75`. Общий запас нефтебаз составляет 500 м³, минимальная потребность
в поставках — 432 м³. Ожидаемый результат:

```text
Общий объём поставок: 432 м³.
Общая стоимость: 110310 руб.
Остатки нефтебаз: [57, 9, 2, 0, 0] м³.
```

АЗС S13 получает 0 м³: после потребления её начального запаса остаётся
10 м³ при требуемом страховом запасе 5 м³.
В тестах также сохранён контрольный пример для двух нефтебаз и трёх АЗС
с оптимальной стоимостью 75 руб.

## Сравнение режимов

| Режим | Способ решения |
|---|---|
| `highs` | Автоматический выбор между симплексным методом и методом внутренней точки |
| `highs-ds` | Двойственный модифицированный симплекс-метод |
| `highs-ipm` | Метод внутренней точки с последующим crossover |

В одиночном расчёте выводятся выбранный режим, время вызова решателя,
число основных итераций и шагов crossover. `highs` обозначает режим
автоматического выбора; фактически выбранный алгоритм отдельно не определяется.

При `--compare` каждый режим сначала выполняет один прогревочный запуск.
Затем проводятся измеряемые запуски на одинаковых данных с изменением порядка
режимов. Прогрев не учитывается в таблице.

| Показатель | Содержание |
|---|---|
| `Успех` | Количество проверенных оптимальных результатов относительно числа запусков |
| `Цена, руб.` | Медиана стоимости успешных результатов |
| `Решатель, мс` | Медиана времени вызова `linprog`, включая внутреннюю подготовку |
| `Весь вызов, мс` | Медиана времени всей `optimize_plan`: проверки, матрицы, решение и сводка |
| `Итер.` | Медиана числа основных итераций |
| `Cross.` | Медиана числа шагов crossover |

Загрузка JSON, сохранение файла и печать отчёта в измерения не входят.

Стоимость, время решателя и числа итераций рассчитываются по успешным
запускам; время всего вызова — по всем измеряемым запускам. Статус `mixed`
в таблице означает, что только часть запусков дала проверенный оптимум.
Если успешных запусков нет, выводятся статус последнего результата и прочерки
для недоступных показателей.

Число итераций разных алгоритмов не определяет их относительную скорость.
Предварительная обработка может решить задачу без основных итераций.
Для выводов о производительности нужны задачи разных размеров;
время на небольшом примере зависит от нагрузки компьютера и расходов на запуск.
